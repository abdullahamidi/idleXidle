## Missed — things in this area the audit did not report

1. **The keystone-socket gate is UI-only for existing saves and for the composer.** `PlayerLoadout.Restore` truncates keystones to `MaxKeystones` (= `Build.KeystoneSlots` = 3), not to `KeystoneCapacity` (`PlayerLoadout.cs:294` vs the skill path at `:290`, which correctly uses `SkillCapacity`). `Build.Take` caps at the constant 3 (`Build.cs:496`) and `BuildComposer.Compose` takes every learned id it is handed (`BuildComposer.cs:145-148`). Only `ToggleKeystone` (`:227`) reads `Math.Min(MaxKeystones, KeystoneCapacity)`. A save written when three sockets were free (before 2026-08-23, `DustEffects.cs:206-209`) keeps wearing three keystones with one socket bought; `socket_2`/`socket_3` (7 spine points) buy nothing for that player and the sim honours unpaid sockets. `Game1.cs:630` sets `KeystoneCapacity` before restore, so the ordering is right — the truncation just does not read it.
2. **The vow gate is UI-only.** `DustEffects.KnownVows` is read at exactly one site, the weave menu (`WeaveScreen.cs:599`). `BuildComposer.cs:165` resolves any saved `VowId` with `Weaving.ById` and `PlayerLoadout.Restore` (`:290-292`) restores any `VowId`. The 11-point vow chain gates what the menu offers, never what the build wears or the sim pays. `DustEffects.KnowsVow` — which the audit lists as dead-to-delete — is the predicate that would close this.
3. **Two caps on one number, again.** `Build.KeystoneSlots = 3` (`Build.cs:489`) and `PlayerLoadout.MaxKeystones` (`:78`) sit beside the tree-driven `DustEffects.KeystoneSockets` (1..3) — the same shape as the `weave_5`/`Unlocks.SkillSlots` duplicate the audit did flag (claim 37). The audit flagged only the stale comment at `Build.cs:475-476`, not the constant it guards.
4. **`Restore` does not re-validate prerequisite closure.** `MemoryDust.cs:192-198` accepts any known id; a save holding `ks_reaper` without `ks_blood_magic` restores as owned and `Spent` charges it. The "one road" shape is enforced only at `Purchase` (`:168-174`). Tolerant by design, but it is a second reason (with claim 28) that node-id or prerequisite edits are save-compat surfaces.
5. **A third consumer of the host-side income rule.** `UnlockFacts.TraitPointsEarned` (`Unlocks.cs:66`) gates the TRAITS screen (`:154`) and is filled from `Game1.TraitPointsEarned`; `unlocks_test.cs:55-57` and `onboarding_test.cs:303` pass hand-typed values for it. Moving the rule to Core lets those tests feed the real number too.
6. **One more site of the stale 34-point budget:** `PrestigeScreen.cs:326` ("two of them cost more than a career earns") — the screen's own remark encodes the "one terminal reachable" assumption the audit shows is false at 28.
7. **`SkillPointsEarned` is not host coupling** (correction to §12, recorded under claim 21): `MasteryPoints.Total` is in Core; only `TraitPointsEarned` needs the move.
